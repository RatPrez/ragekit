# PSO, RBF and XML data files, manifests and audio data

## PSO (binary .ymt, .ypdb, .ymf)

A PSO is the game's second meta container: a big endian file of sections `ident(4) length(4) payload` - `PSIN` (the
data), `PMAP` (root block id and blocks), `PSCH` (the schema: structure and enum descriptions), an optional `PSIG`,
`STRF` / `STRS` / `STRE` (string tables) and `CHKS`. Carcols, carvariations, peds, handling, pedpersonality and the
streaming manifests are PSO files.

`read_pso` / `write_pso` keep every section, so a file comes back byte for byte (1,793 game and server files);
`Pso::update_checksum` recomputes `CHKS`. `PsoView` walks the data with the file's own schema - typed reads by name hash
(integers, floats, vectors, strings, enums and flags, arrays of structures, pointers or primitives, maps) - and
`pso_dump` prints it. `pso_name` resolves hashes from a table of known names (`src/pso_names.inc`, generated by
`tools/gen_pso_names.py`). PSO field and structure names are case-sensitive joaat.

## RBF (creature metadata and more)

The third metadata container (magic `RBF0`) is a binary XML: elements with attributes, typed values (`<pedCompID value="6"/>`:
a uint32, a float, three floats, true / false, a string) and raw content (text, or a `char_array` / `short_array`). The game
uses it for the creature metadata every clothing DLC ships (`mp_creaturemetadata_*.ymt`: the expressions of ped components and
props), for cutscene and Bink movie metadata, and in a few `gtxd.ymt` and `_manifest.ymf` files. Each name is stored once, at its
first use, so `write_rbf` gives back the game's bytes exactly (all 200 RBF files of the Legacy install).

```cpp
RbfNode root = read_rbf(rsc::read_file("mp_creaturemetadata_xmas.ymt"));
for (const RbfNode* item : root.child("pedCompExpressions")->children_named("Item"))
    std::printf("component %u\n", item->child("pedCompID")->value.u32);
rsc::write_file("copy.ymt", write_rbf(root));
std::puts(rbf_dump(root).c_str());   // as XML-like text; rk info <file> prints the same
```

## XML data files (`.meta`)

Most of the game's data files are XML: `vehicles.meta`, `carcols.meta`, `carvariations.meta`, `handling.meta`,
`vehiclelayouts.meta`, `peds.meta`, `pedalternatevariations.meta`, `shop_*.meta`, `content.xml`, `setup2.xml` ... (the base
game ships a few of them as PSO `.ymt` instead, see above). `xml_dom.h` reads them into a tree of elements (name, attributes,
text, children) and writes a tree back the game's way: CR LF, two-space indents, `<name value="1" />` for empty elements.

```cpp
const Bytes b = rsc::read_file("vehicles.meta");
XmlElement doc = parse_xml(std::string_view((const char*)b.data(), b.size()));
for (const XmlElement* item : doc.child("InitDatas")->children_named("Item"))
    std::printf("%s\n", item->child_text("modelName").c_str());
std::string text = write_xml(doc);
```

Written back, every one of the game's 2,857 `.meta` and `.xml` files reads as the same document. Comments and the original
layout are not kept.

## Streaming manifests (`_manifest.ymf`)

`manifest.h` is the typed model of `_manifest.ymf`: ityp dependencies, imap dependencies, interiors with their
collision files, HD texture dictionary bindings and map data groups. `write_ymf` writes the layout CodeWalker writes
(sections PSIN, PMAP, PSCH) and CodeWalker's `YmfFile` reads it back. Names in a manifest are lower-cased joaat hashes
(`manifest_hash`). `rk ymf-make` makes the manifest a custom interior resource needs. The game's own manifests come
back byte for byte through the PSO container (`read_pso` / `write_pso`); through the typed model they come back with the
same content but shorter than the game's (by 20 or 40 bytes mostly, up to 8,892 on the big metadata archives'; about
360 of every fifth file in each edition: the round trip lists them as notes), since `write_ymf` lays the sections out as CodeWalker does, not as the game's tools did.

## Audio data (.rel)

`rel.h` is the container of `audioconfig.dat4.rel`, `speech.dat4.rel`, `*_amp.dat10.rel`, `*_mix.dat15.rel`,
`curves.dat16.rel`, `categories.dat22.rel`, `*_sounds.dat54.rel` and `*_game.dat149/150/151.rel`: a type, a data block
(a version, then the items), the name table, the index (name hash, offset and length per item; audioconfig uses a
string index), and the hash and pack tables (the file positions of the fields that hold hashes of other items and of
wave containers). `Rel` keeps all of it as stored, so `read_rel` -> `write_rel` is byte for byte (all 227 `.rel` files
of the Legacy install and 151 from FiveM resources; CodeWalker's XML of original and rewrite agree). Items are opaque
(`RelItem`: hash, type id, bytes) except the typed dat151 structures an interior needs. The DLC packs also carry the
same files without the `.rel` extension (`.dat4`, `.dat10`, `.dat15`, `.dat54`, `.dat149`, `.dat150`, `.dat151`: 229 in
Legacy), which read and write back the same, and `.nametable` files (229) listing a data file's item names, each NUL
terminated (`read_nametable` / `write_nametable`, byte for byte). PSO files under other extensions (`.cut` cutscenes,
`.pso`) come back byte for byte like the `.ymt` ones.

```cpp
Rel rel = read_rel(rsc::read_file("game.dat151.rel"));
RelItem it;
if (rel.find(joaat_lower("v_apart_midspaz"), it) && it.type_id == dat151::InteriorSettings) {
    Dat151InteriorSettings is = Dat151InteriorSettings::read(it);   // flags, walla sound set, room hashes
}
Rel mine = Rel::make(reltype::Dat151, 45897013);                    // a new file
rel_add(mine, joaat_lower("my_int"), settings);                     // typed items bring their hash-table fields
mine.add(hash, raw_item_bytes, {hash_field_positions});            // or any item as bytes
rsc::write_file("my_game.dat151.rel", write_rel(mine));
```

`Rel::add` pads as CodeWalker's writer does (some dat151 types to 16 bytes, a few to 4), adds the hash and pack table
entries and keeps the index in the game's order (name hashes rotated right by 8, ascending). **The game keys some data
files by the file name up to its first underscore** and refuses a second file with the same key:
`rat_apt01_game.dat151.rel` and `rat_bar01_game.dat151.rel` both have the key `rat` (`rel_data_file_key`);
`interior_dat151_file_name("rat_apt01")` gives `ratapt01_game.dat151.rel`.

## Interior audio (`audio_occlusion.h`)

An interior without its audio files is heard at full volume through its walls and has no reverb. The game wants an
occlusion file (`<proxy hash>.ymt`, naOcclusionInteriorMetadata: portal infos and path nodes) and dat151 items for the
interior and its rooms:

```cpp
AudioOcclusion m = occlusion_from_mlo(archetype, position_of_the_mlo_instance);   // rooms, portals, door entities
m.name = "rat_apt01";
rsc::write_file(std::to_string(m.proxy_hash()) + ".ymt", write_occlusion_ymt(m));
rsc::write_file("ratapt01_game.dat151.rel", write_rel(build_interior_dat151(m)));  // InteriorSettings + an InteriorRoom per room
```

`rk occlusion <ytyp> <out dir> --ymap <ymap>` does the same from files. The recipe - the proxy hash is joaat(archetype)
xor the instance position times 100, truncated per axis; a room's key is proxy xor joaat(room); a path's key is the key
difference plus the hops - follows ht_mlotool and is checked against the game's own file for v_apart_midspaz. The `.ymt` is written the
way CodeWalker's PsoBuilder writes it, and `read_occlusion_ymt` reads any game file (1,431 distinct occlusion files of
the base game and DLC packs rewrite with the same CodeWalker XML). The dat151 items use the game's room defaults
unless you give your own. A change needs a restart of the server, not only of the resource. Not yet heard in game.

## Door and emitter sounds

What the game's files say (Legacy b3889, `update.rpf` `game.dat151.rel` / `sounds.dat54.rel` and the DLC packs):

- **Doors.** The audio of a door model is found by name: a `DoorAudioSettingsLink` (dat151 type 117) named
  `dasl_<model hash in hex>` (`door_audio_link_name`; 401 in game.dat151, 206 in the 38 DLC game.dat151 files read) points at a
  `DoorAudioSettings` (type 47, 438 items in game.dat151: a dat54 sound set, a `DoorTuningParams` item, the max occlusion, 0.7 on most).
  `DoorTuningParams` (type 48, 30 items) are the thresholds at which the audio counts a door open, closed or moving and a
  door type: 4 for hinged doors (0246D335, used by 313 settings: `v_ilev_ct_door01`, `v_ilev_mm_door`, `v_ilev_fh_frntdoor`,
  the fire door), 2 for up-and-over garage doors (`prop_com_ls_door_01`, `prop_gar_door_01`, Michael's and Franklin's), 1 for
  the vertical sliders (the bank's roller shutter `v_ilev_bl_shutter2`, Benny's `lr_prop_supermod_door_01`). The sound set (dat54 type 32) maps script names to sounds: a hinged door has
  `opening`, `closing`, `closed`, `push`, `limit`, `collision` and one name not found (702E09E4), each a tree of variable
  blocks, parameter transforms and multitracks over `RESIDENT/doors.awc`; a garage door has `opening`, `closing` (a synth
  loop), `opened` and `closed` (`SimpleSound`s). This is the audio side; `doortuning.meta` is the
  door's physics (auto-open rate and radius), not its sound.
- **Emitters.** The `effectHash` of an archetype's `CExtensionDefAudioEmitter` names a dat151 `EntityEmitter` (type 7, 52 bytes;
  57 in the files read: the speaker docks, fans, air conditioners, clocks ...): a sound, a max distance (18 to 100 m), the
  chance it plays during business hours, the evening and the night, a cone, a path depth and a broken health.
- **Sounds.** A `SimpleSound` (dat54 type 12) names a wave by `joaat_lower("<wave pack folder>/<awc name>")` (the pack table
  lists it: `RESIDENT/doors`, `dlc_mpheist/...`) and the stream's own name. A looping wave loops through its format chunk's loop
  point: of the simple sounds over looping waves, 2 sit under a `LoopingSound`, the rest under multitracks, wrappers, twin loops.

`Dat151DoorAudioSettings`, `Dat151DoorTuningParams`, `Dat151EntityEmitter`, `Dat54SimpleSound`, `Dat54SoundSet` and
`Dat54LoopingSound` read and write these items (every one of the game's files read writes back byte for byte, its hash and pack
table positions included); `Dat54Header` is the header every dat54 sound carries (a flags word and the fields it names: the
volume in hundredths of a dB, the category ...). `rel_add` puts the sound items' hash references (child sounds) and pack
references (the container) into the tables. A resource ships its own sounds as data files: the dat54 as `AUDIO_SOUNDDATA`,
the dat151 as `AUDIO_GAMEDATA`, a folder of `.awc` as `AUDIO_WAVEPACK` (docs.fivem.net "Data files"; the game's own DLCs ship
`dlcmpheist_game.dat151.rel` and `dlcmpheist_sounds.dat54.rel` side by side, so the one-file-per-key rule is per file type).
Never heard in game.
