# Map files: .ytyp, .ymap and the meta container

## The meta container

A `.ytyp` or `.ymap` is an RSC7 resource (version 2) holding a meta document: structure and enum descriptions plus
data blocks, the structures pointing at each other with 32-bit meta pointers (the 1-based block id in bits 0-11, the
byte offset in bits 12-31). `meta.h` reads and writes that container without interpreting it, so any meta file
round-trips:

```cpp
Meta m = read_meta(rsc::read_file("whatever.ymap"));
rsc::write_file("copy.ymap", write_meta(m));
```

`MetaBuilder` packs structures the way CodeWalker does (one block per type, items padded to 16 bytes, 16 KB per block).
`MetaObject` lifts one structure and everything it points to out of a file, driven by the file's own structure
descriptions or the built-in tables (`src/meta_tables.inc`, generated by `tools/gen_meta_tables.py`), so extensions and
other types without typed fields travel intact.

Not every `.ymt` is a meta file: ped variation infos (`mp_*_freemode_01_*.ymt`, the clothing metadata) are, and
`meta.h` handles them; carcols, carvariations, peds, handling, `_manifest.ymf` ... are PSO files ([pso-and-audio.md](pso-and-audio.md)).

## The typed model (`map.h`)

`read_ytyp` / `write_ytyp` and `read_ymap` / `write_ymap` work on plain structs built on the meta layer:

- `MapTypes`: archetypes - base, time and MLO (interiors: rooms, portals, entity sets, entities, time cycle
  modifiers) - with their extensions, the file's dependencies and composite entity types.
- `MapData`: entities and MLO instances, car generators, box occluders, time cycle modifiers, physics dictionaries,
  the block description; occluder meshes, container LODs, grass and prop instance data and LOD lights are kept as they
  are (`MetaObject`).

Fields the model does not name are written back from each structure's `raw` bytes, and the structure descriptions of
the source file are kept and reused on write (their keys differ between the tools that made game and mod files). A
new model uses the built-in descriptions.

```cpp
MapTypes types;
types.name = joaat_lower("my_interior");
Archetype mlo;
mlo.kind = Archetype::Kind::Mlo;
mlo.name = mlo.asset_name = joaat_lower("my_interior");
mlo.asset_type = 4;                     // assetless
mlo.rooms = {limbo, lounge};            // MloRoom { name, bb_min, bb_max, ... }; room 0 is the outside
mlo.portals = {door};                   // MloPortal { room_from, room_to, corners ... }
mlo.entities = {sofa};                  // Entity { archetype_name, position, rotation ... }
types.archetypes.push_back(mlo);
rsc::write_file("my_interior.ytyp", write_ytyp(types));
```

`examples/make_interior.cpp` builds a complete interior and the `.ymap` that places it.

An MLO instance stores its own orientation; ordinary entities, including those inside an interior, store the inverse
(163 rotated interiors of the game fit their interior proxies one way and none the other way).

### Views of what is kept as objects

`grass_batches(d)` reads the instanced grass of a ymap (`GrassBatch`: the batch's box, scale range, archetype, LOD
distances and its 16-byte instances, positions in 65536ths of the box) and `lod_lights(d)` its LOD lights (`LodLight`:
the CDistantLODLight's position and colour with the CLODLight's direction, falloff, flags, cone and corona for the
same index). `set_grass_batches` / `set_lod_lights` write them back, keeping every byte the views have no field for:
over every 4th ymap of the Legacy install the views written back change nothing. `meta_field(object, "offsetPosition")`
finds any field of a kept structure (an extension, a composite entity type) by its name through the built-in
descriptions; field names hash as written, case and all.

What is left generic, from `rk_unknowns --every=4 meta` (items in every 4th file): of the map files, the archetype
extensions (CExtensionDefParticleEffect 14,564, CExtensionDefLightEffect 7,499 with their CLightAttrDef 9,516,
SpawnPoint 959, Ladder 760, SpawnPointOverride 426, AudioCollisionSettings 305 ...) and the occlude models (739)
are reached through `MetaObject` and `meta_field`; the grass (9.3 million instances in 21,757 batches) and the LOD
lights (165,839 vectors) through the views above. The `.ymt` meta files (ped variations: CPVTextureData 55,216,
CPVDrawblData 11,141, CComponentInfo 11,074 ...; scenarios: CScenarioPoint 39,446, chaining nodes and edges; the
streaming request lists) have no typed model: they read and write through the generic layer.

## Occluders (`occluder.h`)

`occluder.h` decodes what `read_ymap` keeps in `MapData::box_occluders` (16 bytes: centre and size in quarter metres,
the box's length along `(iSinZ, iCosZ)`, the pair scaled to 16384) and `MapData::occlude_models` (a mesh of at most
256 vertices, its indices bytes). `find_occluders_in` lists those that overlap an oriented box. `remove_entities` /
`remap_parent_indices` drop entities from a ymap and renumber the `parent_index` of its child ymaps' entities, whose
LOD links point into the parent's list. The game has 135 occlusion ymaps (9,985 boxes, 1,267 models), all with content
flag 32 and none with entities; `rk_occluder_test` round-trips all of them.

## How the map files are checked

The typed model round-trips field for field and keeps every structure byte outside the pointers; CodeWalker reads the
written files as it reads the originals (the same summary and the same CodeWalker XML). `rk_build_mlo` builds a small
interior with the typed API; `tests/oracle/data/rk_test_mlo.ytyp.xml` is the same interior as CodeWalker XML, and
CodeWalker's conversion of it matches the typed output block for block. See [testing.md](testing.md).
